# Spec: v1.2 Analytics de Margen

**Fecha**: 2026-07-31

**Dependencias**: MVP v1.0 (Reportes) + v1.1 (Proveedores + Órdenes de Compra)

## Contexto y motivo

El dueño ve ventas diarias/semanales/mensuales (v1.0 Reports) y gestiona compras a proveedores con costo real (v1.1), pero **no sabe cuánto gana**. Sin margen por producto, por categoría y en el tiempo, no puede decidir:

- ¿A qué producto le subo precio?
- ¿Qué categoría/rubro me deja más?
- ¿Las ventas del mes son buenas o solo son volumen sin ganancia?
- ¿La decisión de cambiar de proveedor realmente vale la pena?

El BRIEF originalmente marcaba "Analytics Avanzados" como v2.0, contradiciendo el roadmap que lo ubicaba como v1.2. Esta spec resuelve esa inconsistencia fijándolo como **v1.2**, con alcance acotado a **margen de ganancia real** — todo lo demás (predicción de reposición, comparación de proveedores, forecasting) queda fuera para v1.3+.

### Decisiones de diseño (tomadas en brainstorming)

| Decisión | Opción elegida | Alternativas descartadas |
|----------|----------------|--------------------------|
| Usuario objetivo | **Dueño** (rol `admin`) | Manager, cashier (siguen usando v1.0 Reports) |
| Dolor a resolver | **Margen de ganancia real** | Reposición inteligente (v1.3), comparación de proveedores (v1.3) |
| Política de costo faltante | **Fallback jerárquico** con flag "estimado" | Última compra (puede quedar null), promedio móvil (opaco) |
| Alcance funcional | **A + B + C** (KPIs + Top 10 + Categoría) | Solo KPIs (menos impacto), solo Top (queda corta la decisión de precio) |
| Arquitectura de datos | **Denormalización** de `last_cost_cents` en `Product` | Lookup en cliente (N+1), caché en memoria (estado global frágil) |

## Modelo de datos

### `Product` (extensión, sin ruptura)

```typescript
interface Product {
  // ... campos existentes sin tocar
  last_cost_cents?: number;                          // último costo confirmado al recibir
  last_cost_source?: 'purchase' | 'fallback_price';  // auditoría del origen del dato
  last_cost_updated_at?: any;                        // serverTimestamp de la última actualización
}
```

### Reglas de denormalización

1. **Escritura**: en `supplierService.receiveOrderItem()`, dentro de la transacción `runTransaction`, después de actualizar `stock` del producto existente:
   - Escribir `last_cost_cents = final_cost_cents ?? last_cost_cents` (preservar el dato bueno previo si `final_cost_cents` viene undefined/null).
   - Escribir `last_cost_source = 'purchase'`.
   - Escribir `last_cost_updated_at = serverTimestamp()`.
2. **Producto nuevo** (sin `product_id`): al crearse en la misma transacción, incluir `last_cost_cents = unit_cost_cents`, `last_cost_source = 'purchase'`, `last_cost_updated_at = serverTimestamp()`.
3. **Lectura / fallback** (en `marginService.resolveCost()`):
   - Si `product.last_cost_cents !== undefined` → usar ese valor, `is_estimated = false`.
   - Si `product.last_cost_cents` ausente y `product.price_cents` definido → usar `price_cents / 2`, `is_estimated = true`.
   - Si producto no existe (datos huérfanos) → costo 0, `is_estimated = false` (caso patológico, no debería ocurrir).
4. **Defensiva**: `last_cost_cents = 0` se trata como dato válido (no cae al fallback). Esto cubre el caso teórico de un producto recibido a costo cero (promoción del proveedor).
5. **Migración**: productos existentes en Firestore sin estos campos → al renderizar margen, fallback automático a `price_cents / 2` con badge "estimado". No se requiere script de migración.

### Sin tocar

- `sales` — no se modifica.
- `purchase_orders` — no se modifica.
- `supplier_id` y todos los demás campos denormalizados de v1.1 — intactos.

## Servicio `marginService.ts`

### Funciones públicas

```typescript
interface MarginSummary {
  today:      { revenue_cents: number; cost_cents: number; margin_cents: number; margin_percent: number };
  thisWeek:   { revenue_cents: number; cost_cents: number; margin_cents: number; margin_percent: number };
  thisMonth:  { revenue_cents: number; cost_cents: number; margin_cents: number; margin_percent: number };
  estimatedCostCount: number; // cuántos productos usaron fallback price_cents/2
}

interface MarginDaily {
  date: string;
  revenue_cents: number;
  cost_cents: number;
  margin_cents: number;
  margin_percent: number;
}

interface ProductMargin {
  product_id: string;
  product_name: string;
  units_sold: number;
  revenue_cents: number;
  cost_cents: number;
  margin_cents: number;
  margin_percent: number;
  is_estimated: boolean;
}

interface CategoryMargin {
  category: string;
  revenue_cents: number;
  cost_cents: number;
  margin_cents: number;
  margin_percent: number;
}

export async function getMarginSummary(
  range?: { from?: Date; to?: Date }
): Promise<MarginSummary>;

export async function getMarginDaily(
  days?: number                       // default 30
): Promise<MarginDaily[]>;

export async function getTopProductsByMargin(
  limit?: number,                     // default 10
  sortBy?: 'absolute' | 'percent'     // default 'absolute' = margen $, 'percent' = margen %
): Promise<ProductMargin[]>;

export async function getMarginByCategory(): Promise<CategoryMargin[]>;

export async function exportMarginToCSV(
  range: '7d' | '30d'
): Promise<void>;
```

### Funciones privadas

- `resolveCost(product: Product): { costCents: number; isEstimated: boolean }` — aplica el fallback jerárquico documentado arriba.
- `buildMargin(sale: Sale, productsById: Map<string, Product>)` — calcula margen de una venta individual recorriendo `sale.items` y resolviendo costo por producto.

### Convención de unidades

**Todos los campos monetarios de este servicio son centavos** (`*_cents`), igual que el resto del codebase (regla documentada en AGENTS.md). `formatCurrency()` (de `reportService.ts`) divide por 100 al renderizar.

### Patrón de carga

Mismo patrón que v1.0/v1.1: `getSales()` + `getProducts()` completos, agrego en cliente. Firestore no agrega del lado servidor en este stack. Si el dataset crece (>10k ventas), esto se mueve a Cloud Functions — **fuera de v1.2**.

### Filtro para `getTopProductsByMargin`

Cuando `sortBy === 'percent'`, se filtran productos con `revenue_cents < 1000` (10 pesos colombianos, ≈ 1 producto barato unitario) para evitar que una venta aislada distorsione el ranking (ej. 1 unidad × $900 producto y margen 99% → aparece como top, pero es ruido).

## Gotchas y decisiones explícitas

1. **Denormalización en `Product`**: misma filosofía que `Supplier.totalSpentCents` (v1.1). Probada en este codebase, escala bien. Riesgo de inconsistencia mitigado por tests 15 y 16.
2. **Fallback `price_cents / 2`**: mismo marcador que usa v1.1 al crear producto nuevo en recepción (escrito en `supplierService.ts`). Es un "estimado 100% markup", editable después en Inventario.
3. **`last_cost_cents = 0` se preserva**: si un proveedor regala stock (caso patológico pero posible en promoción), el costo 0 es dato válido y NO cae al fallback.
4. **Defensiva en recepción**: `final_cost_cents` faltante NO pisa el dato bueno previo. Priorizamos "no destruir información" sobre "siempre actualizar".
5. **Productos sin `category`**: caen en `'Sin categoría'` (mismo patrón que el placeholder `'General'` que ya usa `getSalesByCategory` actual — pero este usa el campo real).
6. **Filtro de ruido en Top por %**: productos con `revenue_cents < 1000` se excluyen del ranking por margen % (evita que 1 venta aislada distorsione el top).
7. **Solo `admin` ve Márgenes**: el dueño. Manager/cashier siguen con `Reports.tsx` de v1.0 (que no muestra costo).
8. **Sin índice nuevo en Firestore**: el reporte lee `sales` + `products` en cliente y agrega en memoria. Coherente con v1.0/v1.1. Si el dataset crece (>10k ventas), mover a Cloud Functions — fuera de v1.2.
9. **Migración sin script**: productos existentes sin `last_cost_cents` se renderizan automáticamente con fallback + badge "estimado". No requiere backfill.
