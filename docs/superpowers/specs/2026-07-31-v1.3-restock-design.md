## Contexto y motivo

El dueño tiene alertas reactivas de stock (v1.0) y velocidad de venta visible en Reports (v1.0), pero **no sabe cuándo un producto se va a agotar ni cuánto pedir**. Compra por intuición y termina pidiendo de más (capital muerto en bodega) o de menos (ventas perdidas por agotamiento). v1.1 ya capturó `final_cost_cents` por ítem recibido, así que el siguiente paso natural es cerrar el loop completo: **ventas → velocidad → sugerencia → orden de compra**.

El BRIEF ahora marca esta feature como v1.3 en el roadmap (Nov 2026) con score RICE 3.00.

### Decisiones de diseño (tomadas en brainstorming)

| Decisión | Opción elegida | Alternativas descartadas |
|----------|----------------|--------------------------|
| Dolor a resolver | **Reposición predictiva** | Umbral configurable por producto (base necesaria pero separada), comparación de proveedores (v1.4+) |
| Lead time del proveedor | **A — `lead_time_days` en Supplier**, default 7 | Calcular desde purchase_orders (riesgo: 0 órdenes = 0 días = "pedí ya"), híbrido |
| Ventana de velocidad | **A — fija 30 días** | Configurable por producto (complejidad), adaptativa (sesgo con poco historial) |
| Fallback sin datos | **Y — promedio por producto del rubro** | Sin sugerencia (dueño a ciegas), siempre con badge "estimado" |
| Tipo de cálculo del rubro | **B — promedio por producto** | Promedio simple del rubro (ignora cantidad de productos), mediana (robustness sin valor aquí) |
| Output | **A — página dedicada `Restock.tsx`** | Extender StockAlerts (mezcla UX), detalle por producto (no prioriza) |
| Orden | **X — días restantes ASC** | Stock ASC (ignora velocidad), déficit (requiere config de stock objetivo) |
| Acción "Crear orden" | **A con X — modal pre-llenado, una sugerencia por producto** | Crear directo (orden fantasma), solo marcar (doble flujo); batch multi-producto (v1.4) |
| Producto sin supplier_id | **B — mostrar con badge "Sin proveedor" + acción deshabilitada** | Excluir (esconde), proveedor genérico (falsea decisión) |

## Servicio `restockService.ts`

### Función pública

```typescript
interface RestockSuggestion {
  product_id: string;
  product_name: string;
  category: string | null;
  supplier_id: string | null;
  supplier_name: string | null;
  current_stock: number;
  velocity_per_day: number;
  days_remaining: number;            // Infinity si velocity=0
  lead_time_days: number;            // 7 default
  suggested_quantity: number;        // 0 si sin supplier_id
  estimated_cost_cents: number;      // 0 si sin supplier_id
  urgency: 'critical' | 'high' | 'medium' | 'low';
  data_source: 'product' | 'category_avg' | 'insufficient';
}

interface RestockOptions {
  velocityWindowDays?: number;       // default 30
  safetyBufferDays?: number;         // default 7
  minVelocityThreshold?: number;     // default 0.1 (excluye productos <0.1 ud/día)
}

export async function getRestockSuggestions(
  options?: RestockOptions
): Promise<RestockSuggestion[]>;
```

### Algoritmo por producto

1. Calcular `velocity` = unidades vendidas últimos 30 días / 30.
2. Si `velocity < minVelocityThreshold` (0.1) → excluir (no rota lo suficiente para sugerir).
3. Si el producto tiene datos propios (ventas en los últimos 30 días) → `data_source = 'product'`, usar `velocity`.
4. Si el producto NO tiene datos propios pero tiene `category` → `data_source = 'category_avg'`. Calcular `category_avg = (suma de unidades vendidas en la categoría / 30) / (productos de la categoría con velocity > 0)`. Excluir productos sin datos del denominador.
5. Si el producto no tiene datos ni categoría → `data_source = 'insufficient'`, excluir de la lista (no se puede sugerir nada útil).
6. `days_remaining = stock / velocity` (Infinity si velocity = 0, pero ese caso ya se excluyó en paso 2).
7. Si el producto NO tiene `supplier_id` → `urgency = 'low'`, `suggested_quantity = 0`, `estimated_cost_cents = 0`. Se incluye en la lista para que el dueño vea que existe y puede asignarle proveedor.
8. `suggested_quantity = ceil(velocity * (lead_time_days + safetyBufferDays))`.
9. `estimated_cost_cents = suggested_quantity * (product.last_cost_cents ?? floor(product.price_cents / 2))`.
10. Clasificar `urgency` (solo si tiene supplier_id):
    - `critical` = `days_remaining < lead_time_days` (no llegás al próximo pedido)
    - `high` = `days_remaining < lead_time_days + safetyBufferDays`
    - `medium` = `days_remaining < lead_time_days * 2 + safetyBufferDays`
    - `low` = resto
11. Ordenar por `days_remaining` ASC; los productos sin supplier_id (que tienen `urgency: 'low'`) quedan agrupados al final por su urgencia.

### Funciones internas privadas

- `calculateVelocity(sales: Sale[], productId: string, windowDays: number): number` — cuenta unidades en `sale.items` donde `sale.date >= now - windowDays`.
- `calculateCategoryAverage(sales: Sale[], products: Product[], category: string): number` — promedio por producto con datos.

### Carga y performance

`getSales()` + `getProducts()` + `getSuppliers()` en paralelo (mismo patrón que v1.0/v1.2). Iteración en cliente. Con dataset pequeño (<10k ventas), trivial. Si crece, se mueve a Cloud Functions — **fuera de v1.3**.

### Convención de unidades

Todos los campos monetarios (`*_cents`) son centavos. `formatCurrency()` divide por 100 al renderizar (regla del codebase, ver AGENTS.md).

## Gotchas y decisiones explícitas

1. **`lead_time_days` por proveedor**, no por producto. Un mismo proveedor tiene un lead time; los productos que vende heredan ese lead time. Si querés lead time por producto, es v1.4.
2. **Fallback `price_cents/2`** para `estimated_cost_cents` — mismo patrón que v1.2. Si el producto nunca se compró, no tiene `last_cost_cents`, se usa el proxy editable en Inventario.
3. **Productos sin categoría no se agregan al cálculo de `category_avg`** — están en `data_source: 'insufficient'`. Evita inflar el denominador con productos que no venden.
4. **`minVelocityThreshold = 0.1`** — excluye productos con ventas residuales (< 3 unidades/mes). Evita sugerir reposición de artículos de baja rotación.
5. **`safetyBufferDays = 7`** por defecto — cubre el lead time más una semana de imprevistos. Configurable vía opciones del servicio, **no expuesto en UI** (decisión de implementación; ajustar esto requiere tocar el código).
6. **`Infinity` en `days_remaining`** — solo si velocity=0 (caso que ya se excluye en paso 2). El tipo `number` lo soporta.
7. **Productos sin supplier_id NO se excluyen** — se muestran con badge para que el dueño los vea y pueda asignarles proveedor (mismo patrón que v1.2 con badge "estimado").
8. **`PurchaseOrderModal.initialItems` es prop opcional** — no rompe callers existentes. Si no se pasa, modal arranca vacío como hoy.
9. **Sin paginación** — se asume <100 productos. Si el inventario crece (>500), se mueve a scroll infinito o paginación en v1.4.
10. **Sin cambios de reglas Firestore** — admin/manager ya tienen acceso a `suppliers` desde v1.2 security. Esta spec hereda la garantía.
